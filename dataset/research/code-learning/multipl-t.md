# MultiPL-T language transfer

The [original paper](https://arxiv.org/html/2308.09895v6), Tables1,2,4,8 and sections4–5, plus the [author artifact](https://github.com/nuprl/MultiPL-T), establish genuine further training of StarCoderBase. The starting models already know Python and have some target-language ability. Table2 reports peak sampled pass@1 on translated HumanEval. The public repository's older20-sample result CSVs fluctuate around those scores and do not reproduce every paper score; their checkpoint counters support workload reconstruction, not replacements for the paper's selected score.

The work unit is one full language-specific training and checkpoint-selection run, including creation of its synthetic curriculum. It includes all7epochs for1B or10for15B, even when the chosen checkpoint occurs earlier. This avoids assuming the best epoch was known in advance. It excludes other model sizes, language experiments and unrelated ablations. The same generation cost appears in alternative model rows because each describes independently rebuilding that curriculum; these rows must not be summed as distinct historical project expenses. Fine-tuning with an already available dataset would instead use the separately retained training-only component.

## Compute reconstruction

* Architecture: original author-hosted configurations and model metadata give1,137,207,296parameters for1B and15,517,456,384for15B. Both are dense StarCoder architectures using multi-query attention. The source calls them1B/15B. Shared2P coefficients use the retained model totals consistently;6PT is the training approximation, omitting context-dependent attention and small optimizer arithmetic.
* The1B OCaml script packs2048tokens per microbatch. Its final checkpoint21356represents single-microbatch steps; gradient accumulation8must not be multiplied again. Thus the run processes43,737,088tokens. The15B scripts use8GPUs×batch1×accumulation4=32sequences per optimizer step. The retained94step/epoch OCaml and73step/epoch Racket counters yield61,603,840and47,841,280tokens over10epochs. Exact dataset truncation/shuffling at epoch boundaries introduces small differences; the corpus itself is gated and was not accessed. We do not substitute its example count for a token count.
* Generate five test suites for each432,361pre-filter Python functions, with StarCoder15B. Central input/output lengths160/160tokens are estimated from the reported short functions and several assertions per completion; failed suites remain counted. The final table reports133,168translation functions; body prose says133,668, a0.38%discrepancy. Use Table1consistently.
* Translate each function100times for OCaml and50for Racket with StarCoderBase15B, including failed translations. Tokenizing all retained original1,000prompt ablation samples with the study authors’ published StarCoder tokenizer gives138,647OCaml/146,375Racket input tokens in total, or means138.647/146.375per prompt. Add140/110estimated output tokens respectively. The output lengths allow generated failures to exceed the roughly142/118training tokens per retained example inferred from packed epoch totals. The samples are related ablation prompts, not the full generation log.
* Count test generation in full for each independent reconstruction. It is not divided by the five languages. Test generation and translation use the15B coefficient even for the1B student. This accounts for most of the total FLOPs.
* The1B training evaluator sets a maximum512total tokens including the prompt, then trims named stop strings after decoding. EOS may stop generation earlier, so512is a maximum-length allowance rather than an observed count. Its20completions per question and seven checks are counted. The trainer’s initial evaluation callback returns without generation when `checkpoint_dir is None`; it adds no eighth check. For15B, ten analogous512-token checks are an explicit conservative monitoring estimate. They are small next to generation. Inference prompts are counted once per sampled completion, assuming KV reuse during generation and no cross-completion prefix sharing.

[calculate.py](calculate.py) reproduces every component from the retained inputs and prompt samples using `tokenizers==0.21.4` (listed in [requirements.txt](requirements.txt)). It disables padding and truncation and adds no special tokens, matching the tokenizer’s absent postprocessor. The study authors’ [15B tokenizer](https://huggingface.co/nuprl/MultiPL-T-StarCoderBase_15b/blob/main/tokenizer.json) and [1B tokenizer](https://huggingface.co/nuprl/MultiPL-T-StarCoderBase_1b/blob/main/tokenizer.json) are byte-identical (SHA256 `9af07a3123a1f4d75dcb85fbdc4c62f9b7873d23fa39c449d2240c3e33eb3ab5`). The original training scripts load the base tokenizer (`AutoTokenizer.from_pretrained(model)` for1B; `--no_custom_tokenizer` for15B); no new vocabulary is introduced. The base repositories require access, so the authors’ openly published tokenizer files are retained instead. Sensitivity changes full-corpus mean input length to0.8or1.2times the sample mean, generated output length to0.5or2.5times central, and test-generation volume to0.5or2times. Those are accounting scenarios, not statistical intervals. An extra30%on fine-tuning operations for attention has little effect on the total because helper generation dominates. This is much better constrained than hardware-hours×invented utilization, but the missing helper logs remain the main compute limitation.

## Human interpretation

[human-learning.md](human-learning.md) documents the source timings and learning content. These are ordinary learners who already program, conditional on eventually reaching the stated narrow target. The typical1B comparison starts with weaker general programming than the15B comparisons: the paper reports15.1%Python pass@1 for1B versus30.6%for15B. Human hours are not proportional to target-language percentage-point gains. All three assumed human endpoints match by construction; no human cohort was evaluated on these endpoints.

## agen-codexfer-mplt-ocaml1b

OCaml1.5%→9.7% on156problems. Human10hours, sensitivity4–30, for expressions, function definitions, types and elementary list recursion with practice. The author card identifies selected epoch6/revision`e8a24f9e2149cbda8c3cca264a53c2b361b7a031`; compute includes the full seven-epoch selection process.

## agen-codexfer-mplt-ocaml15b

OCaml6.9%→19.9% on156problems. Human20hours, sensitivity8–50, for more reliable typed list/string/option manipulation and mixed function-writing practice. Selected author-card epoch4/revision`e7babda985786810707200ff885df6105de7dc56`; compute includes ten epochs. Table4's novel-format in-context benchmark regresses from50.6% to 42.9%, so the standard benchmark improvement must not be presented as universal OCaml improvement.

## agen-codexfer-mplt-racket15b

Racket11.8%→21.0% on161problems. Human12hours, sensitivity4–35, for Racket collections, recursion and completing specifications from existing Python/Java and rudimentary Racket knowledge. Selected epoch8/revision`f0c77c06482f436f469007f20d731cb9dd73d609`; ten-epoch selection run. This target concerns functional correctness, not idiomatic functional style. The paper's style experiment concerns1B, and is not a measured style score for this15B row.

No exact first-public release dates for the three selected fine-tunes were established. Repository creation dates predate some checkpoint histories and do not establish those revisions' public release. The original StarCoder release is not substituted.

## Assessment reuse and selected-model scores

[The original paper, section 5.2.1](https://arxiv.org/html/2308.09895v6), evaluates checkpoints each epoch and reports peak benchmark performance. The retained `training-init.py` constructs evaluation from the HumanEval file and `trainer.py` calls it at epoch boundaries. This selection uses the assessment questions, whereas the human learning target assumes unseen problems. All three MultiPL-T rows therefore flag `different_assessment` as well as the existing difference in learning inputs. Pass@1 still describes one submitted solution; the twenty generated samples estimate that probability and are not twenty retries credited as one success.

The CSV keeps the model cards' published selected-model values: 9.7% for OCaml 1B, 19.9% for OCaml 15B, and 21.0% for Racket 15B. The retained OCaml epoch logs contain higher values—10.737179% at `eval_15255` for 1B, and 20.512821% at `eval_checkpoint-658` for 15B. Those logs do not independently reproduce the cards' claims that the listed revisions are best-performing. They support the training/evaluation schedule, but the point scores remain tied to the published selected revisions; do not substitute a different log maximum without establishing its model identity. The card epoch labels alone do not resolve the discrepancy. Racket's retained maximum, 20.962733% at checkpoint 584, agrees with its rounded 21.0% card score.
