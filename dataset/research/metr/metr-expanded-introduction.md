# METR: full individual-task expansion

Prepared from fresh public source records, 2026-09-12. `remaining.csv` contains **369 additional task/model rows**, leaving the approved initial 30 rows in `points.csv` unchanged. Together these cover **399 individual-task IDs**. `progress.csv` assigns all **402** IDs a disposition: 30 approved initial, 369 expanded candidates, and 3 unresolved duration-bin work units. `expand.py` is reproducible and does not modify the approved CSVs. `metr-expanded-records.jsonl` contains the exact original selected records; the original repositories and their commit pins remain under `agent-work/sources/`.

## Shared methods and source selections

The reviewed [initial METR method](metr.md) continues to apply: one whole task attempt; arithmetic-mean AI native tokens over **all** published attempts, including failures, multiplied by twice active parameters, plus attention over the context. `tokens_count` is inclusive of cache reads, and the exports' own `generation_cost` puts the billed price per counted token at or above the model's uncached input price on every alias whose rate card is identified, so the prefix was recomputed and every counted position is charged a weights pass (`cache-accounting.md`, Damon 2026-09-16). The 2026-09-14 to 2026-09-16 near-perfect-caching rebuild is withdrawn. No successful-run conditioning, dollar conversion or success-normalization is applied to compute. Native totals are not falsely relabeled input/output totals. Every selected individual task/model has complete positive token records, so no missing-token imputation is necessary. All selected source human ratings have human_source=baseline. Human time is the reported successful-run geometric mean human_minutes × 60, and human_attempts counts all recorded successes. Human performance uses **all** human outcomes, not an imaginary perfect baseline inferred from successful-only timing. The source's human pseudo-durations commonly do not reproduce its rating and are not substituted for it.

For each task/model, prefer TH1.1 if the exact alias exists, otherwise TH1.0. This is an explicit latest-public-record selection, not an average across releases. DeepSeek-R1, gpt-oss and davinci-002 use TH1.0. GPT-4's Atari-paper question also falls back to TH1.0. Task ratings and baselines always come from the same export as the selected AI runs. Release-specific timing changes are retained; for example local-research and TeX questions have different human records/ratings across releases. Each point records exact task versions and source scaffold. A source-mapped version match is used where human records omit versions; we cannot independently reconstruct what changed between unpublished task revisions.

Scaffolds include flock-public, modular-public, Inspect ReAct, Inspect triframe, and the SWAA init_solver/generate combination. METR records sometimes list both task-start and agent solvers in one scaffold string. We retain those strings, not infer multiple independent attempts from them. The raw run totals do not provide a role-by-role token split or settings pack. As in the reviewed initial method, all native tokens are assigned the primary coefficient, explicitly including any helper roles. This is an assumed-model-identity accounting approximation, not evidence that every scaffold uses one role. Exact original run IDs and native tokens are below. No separately measurable image-model calls or training work is added based only on a task's subject: image_labeling is code construction, not a VLM labeling benchmark.

All model coefficients, original analyses, and transfers are documented in [metr-expanded-models.md](metr-expanded-models.md). GPT-4o and GPT-5 retain the shared 50B and 100B active coefficients. Separate METR model IDs avoid falsely attaching an exact API snapshot/reasoning setting to an alias that does not resolve it. The davinci-002, o1 and Gemini 3 Pro estimates particularly depend on broad model-scale transfers.

## New task and protocol judgments

**SWAA:** [METR appendix A.1/B.1](https://arxiv.org/html/2503.14499v2#A1) describes short decisions, code completions and arithmetic. Relevant METR employees timed the response in a webapp; general instructions precede timing. The work unit explicitly includes reading the question and giving one answer, with context already acquired. Arithmetic leads explicitly say “in code context”; we therefore select complex_1/complex_10, corresponding to the documented software-themed arithmetic variant, not standalone arithmetic. This corrects the initial provisional disposition. These are direct timings, not an estimate scaled from whole coding tasks. Expert describes the actual selected relevant employee baseline.

**Image labeling:** [METR's Claude 3.7 evaluation task table](https://metr.org/evaluations/claude-3-7-report/) describes writing a Python predictor from an image/label generation specification and an example pickle. The layered-squares work unit is therefore coding. It is not one manually labeled image, and no invented image count or encoder cost is applied.

**ICLR:** the [public task description](https://github.com/METR/public-tasks#scrape-email-addresses-of-research-paper-co-authors) specifies an attributed CSV of author names/emails. The title “rank authors” in the supplied identity lead is corrected while retaining the original task IDs. No count is inferred by assigning the README's approximate 500/1500 quantities to an undocumented exact variant. The underlying success rate and continuous collection score both matter.

**Other tasks:** HCAST's [primary PDF task table](https://metr.org/hcast.pdf) supplies the code-repair, recovery, local-research, cryptographic and web-challenge work descriptions. Withheld variants use conservative family descriptions plus exact exported task IDs rather than manufactured prompt contents. ACDC's family description includes gradient/checkpointing and memory debugging; oxDNA is fixing simulation input, not running an entire scientific study. The [Claude 3.7 task table](https://metr.org/evaluations/claude-3-7-report/) also supports the smart-contract exploit family.

**Claude 3.5 revision:** the supplied task lead does not distinguish Old versus New. Select the New October 22 revision for all 36 comparisons, with the choice explicit in point notes and model ID. This is a source selection assumption, not a claim that the generic lead establishes an API revision. Old and New outcomes are not mixed.

## Performance judgments

`metr-expanded-judgments.json` contains an explicit task/model judgment for each candidate, and the sections below give its concrete counts and graded means. Labels are manually specified following inspection of all task outcome matrices; the extraction script does **not** calculate labels from a global threshold.

Material task-specific decisions include: grid level 3 compares near-perfect continuous prediction scores; blackbox tasks consider query-efficiency/solution scores as well as threshold success; complete file recovery gives weight to actual full recovery, not only mean recovered fraction; top-25 ICLR accepts approximately equal collection scores as comparable, while top-5 AI failures remain below the smaller complete-collection target; code-repair tasks consider passed tests and completion; factual questions with one isolated failure in four or more attempts can be broadly comparable, while repeated failures support below. Rare human completion on ACDC does not erase the fact that some humans solve the task and the weakest models never do. Newer models' much higher ACDC success is above. These are best estimates, not formal equivalence tests or claims of established significance. Sample counts stay visible so a reviewer can contest particular judgments.

## Duration bins

The three IDs agen-metr2-30min-opus45, agen-metr2-2h-opus45 and agen-metr2-8h-opus45 identify nominal duration groups, not concrete tasks. The source token-distribution analysis uses bins of 1–4, 4–15, 15–60, 60–240 and 240+ minutes. A “30 minute” representative could therefore mean a nominal bin midpoint or a measured task-average time; the “8 hour” group has no finite upper bound. Neither the task set, weighting nor the human/performance aggregation is established by the supplied leads. Constructing numeric rows would silently choose a different work unit and risk treating a nominal duration as a measured human timing. They are retained as **unresolved_work_unit** in all402 coverage, without fabricated observations. A future aggregate can use an explicitly specified source task set, appropriate sample units and a new reviewed aggregation definition.
