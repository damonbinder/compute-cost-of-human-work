# Public Ariane floorplanning run, January 2022

## sci-chip-floorplan-ariane-2022

This is a new work unit, separate from the proprietary TPU lead `sci-chip-floorplan-alphachip`. Start with the randomly initialized public Circuit Training policy and the Ariane RISC-V block netlist; run the published 200-iteration training/search procedure, then retain its best floorplan. This is **full_training** as an algorithm for solving this particular placement task, compared with human **task_performance**, not human acquisition of a physical-design career. It includes the whole run, not only updates before the selected best checkpoint. It excludes manufacturing, complete chip design, detailed routing and initial CPU architecture development.

Primary evidence is Google's [January 2022 run record](https://github.com/google-research/circuit_training/blob/532801b/docs/ARIANE.md), saved in `agent-work/sources/robotics-science/ariane-run-2022.md`. The corresponding [model](https://github.com/google-research/circuit_training/blob/532801b/circuit_training/model/model_lib.py), training and collection code are saved alongside it. The run record reports nine runs using three seeds, 200 iterations per run and approximately 107K gradient updates. Its mean proxy wirelength, congestion and density are 0.1013, 0.9174 and 0.5502 before coordinate-descent postprocessing. We estimate **one** such run, not all nine. The reported quality is the best placement selected from each completed run; all 200 iterations are charged.

### Matched human output

The task has 133 hard macros. The public netlist/placement metadata has 799 soft macro clusters, and the policy sees a padded graph with 4700 node positions and 28,400 edge positions. Inspecting the original paper's [Extended Data Figure 4](https://doi.org/10.1038/s41586-021-03544-w), the same Ariane design consists largely of repeated memory-block shapes arranged around a central standard-cell region. That figure illustrates the problem geometry; it is not the specific January 2022 output. The run record says its proxy metrics are comparable to the original fine-tuned results.

Estimate **16 active expert hours** to produce a similarly serviceable macro floorplan using ordinary CAD and placement/routing feedback. This is much smaller than the proprietary TPU's several-week task. It includes about two hours to read block connectivity and constraints, about 4.5 hours to group and initially place the 133 repeated macros (roughly two minutes per macro, using grouping), six hours across revisions driven by wirelength/congestion feedback, and 3.5 hours for final clearance, channel and placement checks. Repetition and tool-assisted movement make this feasible over about two active working days; the human is not manually placing every standard cell. Unattended EDA runtime is excluded. The bounds move the revision term, the one component whose size is set by something other than the block's own geometry. The central's six hours of feedback-driven revision is about four rounds. At two rounds the total is 12 active hours, 43,200 seconds; at eight rounds, with a longer initial placement, it is 28 hours, 100,800 seconds. Those are the row's bounds, and they are not observed timing data.

The comparison is match by construction to a plausible macro placement with comparable proxy quality, not an observed human score for this source run. The human has CAD tools and the trained solver has a discrete grid and force-directed placement, so record different inputs/tools. No experimental human attempts are reported.

### Direct neural workload

The historical run settings give 200 iterations, 1024 accepted episodes per iteration, sequence length 134, global training batch 1024 and four epochs. Thus:

- Training positions = 200×1024×134×4 = **109,772,800**.
- Gradient updates = 109,772,800/1024 = **107,200**, agreeing with the published approximately 107K.
- Accepted collection episodes = 200×1024 = **204,800**, each placing 133 hard macros.

The sequence length includes the terminal position. We count its evaluation in training even though the loss may mask a terminal contribution. The policy and value share weights, but their historical wrappers invoke the shared network separately. The central estimate counts independent trunk execution for each wrapper, while allowing unused output heads to be pruned.

Historical model settings are width 8, three graph layers and one dense edge layer per graph update. Edge inputs concatenate two endpoint embeddings plus edge weight, so dimension 17. The model computes both edge directions, including padded positions. The dominant forward term is 3×2×2×28400×17×8 = **46,348,800 FLOPs**. Count multiply and add separately. There is also node projection, scatter/mean aggregation, current-node attention and small policy/value heads. Unlike the original paper's width-32 model, this count uses the released experiment's width-8 graph.

`count_ariane.py` itemizes a joint trunk-plus-both-heads forward of **57,610,364 FLOPs**. This is component bookkeeping, not a claim that one such execution supplies both PPO paths. Split it into trunk **54,382,188**, policy head **3,225,600**, and value head **2,576**. Thus one actor call costs **57,607,788** and one value call costs **54,384,764 FLOPs**. The five transposed convolutions follow the historical implementation, including its final stride-one layer. Aggregation and nonlinear arithmetic are explicitly approximated.

The historical [policy and value wrappers](https://github.com/google-research/circuit_training/blob/532801b/circuit_training/model/model.py) each call the shared network independently. The [historical agent](https://github.com/google-research/circuit_training/blob/532801b/circuit_training/learning/agent.py) uses stored collection value predictions when computing returns and advantages during preprocessing. Contemporary TF-Agents [PPO policy](https://github.com/tensorflow/agents/blob/v0.11.0/tf_agents/agents/ppo/ppo_policy.py) and [PPO agent](https://github.com/tensorflow/agents/blob/v0.11.0/tf_agents/agents/ppo/ppo_agent.py) show the actor and stored collection-value calls, and separate policy-loss and value-loss paths. Version 0.11 is a contemporary implementation reference, not an established exact installed version for this run. These files are saved under `agent-work/sources/robotics-science/ariane-wrappers-2022.py`, `ariane-agent-2022.py`, and `tf-agents-v011-ppo-*.py`.

Forward plus reverse-mode gradients is approximated as three forwards for each execution path, giving **335,977,656 FLOPs per training position** and **36,881,208,036,556,800 FLOPs** for training. This approximation is exact in leading dense-product order and approximate for scatter/activation terms. We do not assume shared weights imply common forward execution or merged reverse-mode paths. Unused-head pruning is a separate, explicit analytic assumption. No extra preprocessing value pass is charged because the collector stores value predictions. Adam uses an envelope of 120K parameters and 12 scalar operations per parameter per gradient update, adding **154,368,000,000 FLOPs**; this envelope is not a claimed model parameter count.

### Collection, evaluation and non-neural helpers

The historical run used 500 collection workers, and the historical collect loop continues generating episodes while the learner updates. The replay buffer is cleared between policy iterations, so accepted episodes alone omit discarded old-policy work. Assume **one extra completed episode per worker per iteration**, adding 100,000 episodes beyond the accepted 204,800. This is an explicit allowance, not a recorded discarded-episode count. It corresponds to roughly one collection cycle during policy publication and learning; training remains the dominant cost. Zero to four extra episodes per worker changes total compute by approximately -4.3% to +12.8%, rather than determining the order of magnitude.

Collection uses separate actor and value calls: 304,800×133×111,992,552 = **4,539,998,869,996,800 FLOPs**. Assume **200 additional evaluation episodes**, giving 200×133×57,607,788 = **1,532,367,160,800 FLOPs**. This is a monitoring allowance, not a reported count or one evaluation synchronized to each training iteration. The [historical evaluation loop](https://github.com/google-research/circuit_training/blob/532801b/circuit_training/learning/eval_lib.py), saved as `agent-work/sources/robotics-science/ariane-eval-2022.py`, runs an episode, fetches variables, writes summaries and sleeps 20 seconds; that sleep does not establish exact episode cadence. It loads the greedy policy, so evaluation is charged the actor path alone. No additional full GPU allocation multiplier is applied.

Force-directed standard-cell-cluster placement occurs after each rollout to compute reward. The run record specifies three 100-step phases, with repulsion disabled in the first phase. Use 799 soft clusters and 133 fixed macros. Approximate attraction by 300 sweeps×28,400 edges×20 floating operations, and repulsion by 200 sweeps×799×(799+133) pairs×20 operations. The latter is a conservative dense pairwise analogue; spatial pruning would reduce it. This gives **3,149,072,000 FLOPs per episode**, or **960,466,960,000,000** across collection and evaluation. The 20-operation constants represent vector displacement, weighted force and coordinate accumulation; they are assumptions about the geometry helper, not CPU peak rates. The padded edge count is an upper proxy for the attraction list. Integer graph management and container operations are not converted to FLOPs. The optional later coordinate-descent refinement is excluded because the selected quality precedes it.

### Result and limitations

Total = training + collection + evaluation + force-directed work + Adam = **42,383,360,601,714,400 FLOPs**. The complete arithmetic is in `research/ariane-operations.json`. No hardware-utilization fractions enter this result. The main workload counts are reported; discarded collection and helper arithmetic remain assumed, so use `derived_assumed_inputs`. The larger uncertainties include possible execution reuse, whether padded/terminal computation is optimized away, and excess collection. If a runtime reused the common trunk forward but retained separate reverse paths, total work would be **34,209,108,664,808,800 FLOPs**. Reusing both forward and backward trunk work would give **22,269,738,571,036,000 FLOPs**. Neither optimization is established for the historical run, so these are explicit alternative execution scenarios, not the central estimate or confidence bounds.

This estimate does not transfer these counts to a proprietary TPU. The supplied netlist metadata contains a March 2022 header even in the historical code snapshot; use its geometry counts as the supplied public design description, not proof of the precise timing of file creation. Core graph/training settings and 133 macros are independently given in the run record and original paper. Exact public availability of the evaluated trained checkpoint is not established, so release date remains blank.
