# Support and workplace agents

Four fixed-weight task-performance observations. The two support points average each source-defined collection. The company and desktop points cover one identified task each; their results are not collection-wide success rates. Human durations are new task estimates, not measurements or benchmark time limits.

## Accounting and reproduction

Run `python recompute_workplace.py --sources SOURCE_DIR --models MODELS_CSV --output NEW_JSON`. The only third-party dependency is `tiktoken`; the vocabulary is retained, so tokenization needs no network access. Output refuses overwrite. `workplace-audit.json` retains per-run inputs, outputs, outcomes and deduplicated usage records. Model records are unchanged copies of the reviewed registry: Sonnet 3.5 October, Sonnet 3.7 and Sonnet 4.5 each use 100B assumed active parameters; GPT-4.1 uses 50B. These are shared estimates, not vendor disclosures. A factor-two coefficient scenario is appropriate and scales the main workload linearly.

**Worker boundary:** customer simulators and simulated coworkers are the environment supplying requests/information, not helpers performing the worker's task. Their compute is excluded, just as customer or coworker time is excluded from the human worker duration. Actual worker calls, repeated attempts within a run and helpers belong inside the boundary. The telecom audit separately retains all simulator input/output counts, allowing a future two-role comparison. Retail logs expose simulator price, not its separate native token counts; no token count is inferred from that price. Company coworker calls are not separately logged in the worker trajectory. Scoring calls after task execution are assessment overhead, not work toward its deliverable.

The main parameter-times-token recipe counts newly processed input, cache creation and output. Cache reads do not receive another full parameter pass and are excluded when recoverable. As with the shared coefficient, context-dependent attention arithmetic is outside the parameter term; `compute_flops` carries it separately (`research/attention-correction.md`), so attending to cached keys/values is not priced at zero. Full-prefix totals remain in the audit as an alternative, not a universal dataset rule. Retail has no native cache decomposition; the released agent supplies no explicit caching directives, so its reconstruction assumes full-prefix processing. Model-side unlogged retries are not invented; all visible calls, errors, tool invocations and failed task outcomes are retained.

## agen-work-taubench-retail

Original sources: [released Sonnet trajectories](https://github.com/sierra-research/tau-bench/blob/main/historical_trajectories/sonnet-35-new-retail.json), [README model identification](https://github.com/sierra-research/tau-bench), [tool-calling agent](https://github.com/sierra-research/tau-bench/blob/main/tau_bench/agents/tool_calling_agent.py), [original paper](https://arxiv.org/abs/2406.12045). These are the original task version, not the later repaired tau2/tau3 tasks. The README identifies the newer Sonnet as `claude-3-5-sonnet-20241022`. No GPT-4o result is substituted.

The file contains 920 complete runs: 115 task IDs, eight trials each. There are 637 successes (69.239%). The unit is one attempt, not eight attempts pooled to get one success. Native usage is absent, but each full message history is released. The agent code sends its policy/history and all tool schemas for every model call. The calculator reads all 16 schemas, including `think`, and reconstructs each preceding message prefix, then adds the actual retained response text/tool arguments. It uses cl100k as an explicit Sonnet tokenizer proxy, four formatting positions per message and three for the response prefix. Tool-call serialization is approximate; source IDs are metadata, not user text. The 2,430-token serialized tool-schema block is repeated per call. Result: mean 13.722 calls and **78,463.807 text tokens**, hence **1.56927613e16 FLOPs**.

This is `derived_assumed_inputs`: original trajectories support task-specific content, while tokenizer and provider schema serialization remain assumptions. A ±25% workload scenario is more useful than pretending the reconstructed count is a measured usage statistic. The retained GPT-4o file was an initial locator check only and supplies no candidate values.

**Human baseline: 480 seconds, trained support worker.** Read task instructions at IDs 0,12,24,36,48,60,72,84,96,108 and their retained conversations, and inspect the complete task action inventory (mean 5.061 ground-truth actions). Work includes authentication, finding the correct order, checking product variants/prices, explaining policy restrictions, securing confirmation and applying changes. These are not simply five button presses: customers sometimes change their minds, withhold item identities or impose several conditional preferences. Examples include exchanging two products with different constraints; an over-budget order with several fallbacks; switching both address and item variants; and choosing which of two tablets to return.

An eight-minute active estimate allocates about one minute to identity/request clarification, two to account/order/product lookup, two to options and confirmation, two to executing/rechecking changes, and one to closing or escalation. Faster straightforward returns offset longer multi-item branches. Use 4–15 minutes as a duration scenario. The worker may use equivalent account lookup tools and ordinary policy references; no whole-policy rereading for each customer is assumed. Approximately 90% correct policy-compliant completion is an explicit trained-worker judgment, not a measured human result. The observed 69.24% agent rate is below that baseline; the classification remains below over an 80–95% reasonable worker-performance scenario.

## agen-work-tau2-telecom

Original [four-trial GPT-4.1 release](https://github.com/sierra-research/tau2-bench/blob/main/data/tau2/results/final/gpt-4.1-2025-04-14_telecom_default_gpt-4.1-2025-04-14_4trials.json) identifies the exact endpoint, temperature zero and source commit `f125e68a2cdc6161f11a4c611413ea4a0918edac`. The file contains all task specifications and device/account initial conditions. The [original paper](https://arxiv.org/abs/2506.07982) describes the cooperative troubleshooting setting. The inventory's GPT-5 mention is a lead only; these values concern the identified GPT-4.1 run.

There are 456 runs, four per 114 tasks, with 156 full successes (34.211%). Each model-produced message has `usage.prompt_tokens` and `usage.completion_tokens`. Sum those once for `assistant` messages only; tool results are already included in subsequent native prompts and are not added separately. Before separating cache reads, this gives **135,969.849 positions per attempt** and **17.072 agent calls**. The corrected main workload is **22,878.761 newly processed input/output tokens** and **2.287876096e15 FLOPs**. Simulator calls separately average **27,584.184 newly processed tokens**, or 82,555.132 including cache reads; neither count is worker compute. There is no separately reported reasoning component to add.

The source usage record omits cache details, but its per-message cost preserves them. The [first public release](https://github.com/sierra-research/tau2-bench/blob/37199f36924c8896f5e048360691f8476cd89ba1/src/tau2/utils/llm_utils.py) computes `completion_cost(response)` before retaining only prompt and completion fields. The release config disables whole-response caching. [OpenAI's original April 14 launch pricing](https://openai.com/index/gpt-4-1/) is $2 per million fresh input tokens, $0.50 cached input, and $8 output. Consequently `cached = (2*prompt + 8*output - 1e6*cost)/1.5`. All 7,785 worker calls yield integer multiples of 128 between zero and their prompt counts; cached input sums to **51,569,536 positions**. The calculator checks the same relationship for simulator calls. This inverts a known accounting equation to recover an omitted counter; it does not infer FLOPs from dollars. Cache creation is within the uncached prompt count, rather than a separately reported addition. Use `input_cache_creation_output`.

The embedded f125e68 revision is not available in the public repository; the June 10 first release supplies the inspected code, while the recordings themselves date June 4. Exact per-call agreement supports the reconstruction despite that revision limitation. Retain **1.359698487e16 FLOPs** as the full-prefix alternative. Reviewed source locators and rates are in `agent-work/sources/workplace-agents/review-accounting-evidence.md`.

**Human baseline: 600 seconds, trained support worker.** Inspect all 114 task IDs/issue inventories and the full task instructions and example conversations for the data, service and MMS branches, including easy/hard personas. There are 36 mobile-data, 29 service and 49 MMS cases, with a mean 4.254 underlying issue flags. Ground-truth required actions average 4.526, but do not enumerate every diagnostic conversation step. Cases combine airplane/data/roaming settings, exhausted allowance, APN corruption, application permissions, misplaced or locked SIMs, and contract suspension. A correct policy referral is a valid target when an issue is beyond available authority; the worker is not assumed to bypass a locked SIM or invent unsupported operations.

Ten active minutes allows roughly 1.5 minutes for authentication and problem triage, 5 for sequential diagnosis and customer instructions, 2 for account/device interventions and 1.5 for verification or a properly recorded referral. This is about a minute per underlying issue plus common communication overhead, not a claim that each issue independently takes a measured minute. Customer waiting, hold queues and physical reboot delays are excluded from worker active effort. Use 5–20 minutes as a scenario. An approximately 90% compliant-resolution target is a judgment for trained staff using the supplied policy and tools; even an 80% baseline is substantially above the recorded 34.21%. No empirical human success rate or timed cohort is claimed.

## agen-work-agentcompany

Original task: [employee reconciliation](https://github.com/TheAgentCompany/TheAgentCompany/tree/main/workspaces/tasks/admin-employee-info-reconciliation). Run: [OpenHands 0.28.1 with Sonnet 3.7](https://github.com/TheAgentCompany/experiments/tree/main/evaluation/1.0.0/20250510_OpenHands-0.28.1-sonnet-20250219), trajectory timestamp May 9, 2025. The retained task, evaluator, original gzipped trajectory and result specify the deliverable. The source ends with 7/7 checks, not merely an agent assertion of success.

The initial CSV has 16 employees. The completed file has 17, adding Priya Sharma, correcting Chan to Chen Xinyi, completing Sophia Rodriguez's phone and replacing Zhang Wei's unknown phone. Read both CSV observations, the directory observation, direct-message actions and final file; `company-action-audit.json` is a compact extraction alongside the unchanged native record. Ordinary coworker responses are external information. The worker's model endpoint is explicit in each response.

Action and observation events duplicate the same `model_response`; deduplicate by response ID and assert the objects agree. There are **31** unique calls. In these native LiteLLM records, prompt tokens already include cache reads but cache creation is separately reported: first reconstruct total input as `prompt_tokens + cache_creation_input_tokens`; then subtract the included cache reads for newly processed input. The native sums are prompt 1,159,590, cache reads 1,159,432, cache creation 70,517 and output 4,407. Thus the main workload is `prompt - cache_read + cache_creation + output` = **75,082 tokens**, giving **1.50164e16 FLOPs**. Use `input_cache_creation_output`. The **1,234,514-position / 2.469028e17-FLOP** full-prefix total remains an alternative; it charges the cache reads for a full parameter pass again. The audit retains every component for scrutiny.

Browser screenshots are stored in the trajectory, but original OpenHands 0.28.1 `conversation_memory.py` only sends set-of-marks images when `enable_som_visual_browsing` is enabled; `agent_config.py` defaults it to false. The reconstruction follows that default accessibility-text mode. The release does not retain an overriding agent config, so this is an explicit input-mode assumption, not proof from the mere presence of screenshot bytes. If evidence of an enabled override appears, native FLOP positions remain valid but text/visual separation needs revision; no base64 screenshot string is counted as text here.

**Human baseline: 1,200 seconds, administrator, matched quality.** Allow 3 minutes to open the source file/directory, 6 to reconcile 17 names/emails and identify discrepancies, 6 to request/check the missing or suspect details, 3 to edit and 2 to verify all records. Waiting for colleagues is excluded. This requires actual comparison and checking, not copying the agent's four known answers in advance. A 12–35-minute active scenario is reasonable. The target is the same complete correct reconciliation, so match is by construction. One selected successful task says nothing about the full AgentCompany collection success rate.

## agen-osworld

Original task UUID `030eeff7-b492-4218-b312-701ec99ee0cc`, enable Chrome Do Not Track. The [OSWorld-Human reference](https://github.com/WukLab/osworld-human/blob/main/chrome/030eeff7-b492-4218-b312-701ec99ee0cc.json) gives a five-action route through `chrome://settings/cookies`. These are manually determined actions, **not recorded human timing observations**. The [Sonnet 4.5 15-turn release](https://huggingface.co/datasets/xlangai/ubuntu_osworld_verified_trajs/blob/main/claude-sonnet-4-5-20250929_15steps.zip) supplies the October 30, 2025 run. Selected by the first Chrome reference task, not by its success. Its final state check is 0.0; the transcript ends still navigating privacy settings. The failed attempt includes all 15 model calls; the limit is not the human duration.

The source ZIP's central directory and the selected text entries were read using HTTP byte ranges; no full screenshot archive was required. `osworld-zip-index.json` records member offsets and compressed sizes; `osworld-dnt-runtime.log`, `traj.jsonl` and `result.txt` are the original extracted bytes. Runtime records identify `claude-sonnet-4-5-20250929` and give **210,049 total multimodal input/output positions**. Output includes the first-call thinking block, so it is not added a second time. A nearby earlier public adapter at commit `d2ae0f697db913c6751cc34b6bb5b3fb3c7de7bf` (August 12) resizes to 1280×720 and supplies one image per model turn. It does not yet support Sonnet 4.5 or the runtime's REGULAR SCRATCHPAD branch, so it is an explicit code proxy, not the exact deployed revision. The corresponding image-filter routine retains old tool-result images until at least ten removals are possible. Independently, every one of the 14 native input increments equals the preceding output count plus exactly **1,270 new positions**, with no history drop. This supports one retained screenshot/result per turn and 1+…+15 = **120 image presentations**. The transcript's coordinate-to-pyautogui scaling also agrees with a 1280×720 API view of the 1920×1080 desktop. Exact internal image encoding remains estimated. Cache creation/read counters are zero in this Bedrock run. Independent review also extracted the archive's original `args.json` and verified its ZIP CRC: 1920×1080 desktop, 15-step cap, screenshots, the exact Sonnet 4.5 Bedrock endpoint, thinking enabled and ISP disabled. Its generic max-trajectory-length value is 3, but native prompt growth shows that this agent did not truncate to three turns.

The official [vision coordinate specification](https://platform.claude.com/docs/en/build-with-claude/vision-coordinates) counts `ceil(width/28) × ceil(height/28)` visual positions: 1,196 for this size, below the standard cap. Treat application to this historical run as an estimate. Visual positions total **143,520**; the CSV text count is **66,529**, excluding them. The older approximate pixels/750 convention would give 147,456 visual positions and 62,593 text positions; this changes the split, not the native-position backbone total. Current documentation was readable through the web tool; direct HTML retention returned 403. URLs and this extracted numerical rule preserve the basis without claiming retained full HTML.

Backbone arithmetic is `210049 × 200B = 4.20098e16`. Add a deliberately explicit image-encoder proxy: original [ViT Table 1](https://arxiv.org/abs/2010.11929), ViT-L/16, 307M parameters, 24 layers, width 1024. For 1280×720, use 3,600 patches plus one class position. Per presentation: `2 × 307M × 3601 + 4 × 24 × 3601² × 1024`. Across 120 presentations this is **4.18289007e14**, or **0.99%** of the resulting **4.24280890e16 FLOPs**. This is not a disclosure of Anthropic's encoder architecture. Encoding only 15 newly seen images instead of all retained presentations reduces the added proxy eightfold and the total by less than 0.9%; use that as a preprocessing-cache scenario. Even a doubled encoder proxy matters less than the shared backbone coefficient uncertainty.

**Human baseline: 60 seconds, ordinary desktop user.** The required outcome is a single browser setting, not reading privacy advice or handling an account. Allow about 10 seconds to recognize the request, 20 to reach the privacy controls via menu/address/search, 20 to locate and enable the setting, and 10 to confirm. A familiar user following the five-action reference could finish faster; an unfamiliar user might take 2–3 minutes. This one-minute estimate assumes successful completion and is not measured, nor inferred from agent wall-clock time. The single observed failure supports below for this run, not a claim that Sonnet always fails this task or that humans have a measured 100% rate.
